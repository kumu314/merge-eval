# 静默失败分诊（Windows + agent）

这一族唯一的共同点：**成功信号为真，事实为空**。所以规则只有一条——断言的层级必须比"命令自己的输出"更低一层：读回状态、比对 SHA、数命中条数。

## 1. 管道让 `$?` 说谎（bash 与 cmd；PowerShell 不在这条里）

- **现象**：`python x.py | tail -3; echo $?` 永远输出 0，脚本崩了也报成功。这是最容易在长会话里连犯三次的同类错误。
- **根因**：`$?` / `%ERRORLEVEL%` 是管道**最后一个**命令的状态，不是你要测的那个。
- **各 shell 实测取值**（python 以 3 退出，管道尾命令自己退 0 或 1）：
  | shell | 直跑读到的 | 接进管道再读的 | 结论 |
  |---|---|---|---|
  | Git Bash 5.2.37 | `$?` = **3** | `$?` = **0**，`${PIPESTATUS[0]}` = **3** | 说谎，且说谎时看起来完全正常 |
  | cmd | 换行后读 `%ERRORLEVEL%` = **3** | `%ERRORLEVEL%` = **1**（尾命令 `findstr` 的码） | 说谎，读到的是尾命令码；`!ERRORLEVEL!` 也救不回来，它照样是 findstr 的码 |
  | PowerShell 5.1 | `$LASTEXITCODE` = **3** | `$LASTEXITCODE` = **3** | **不受影响**，别去"修"PS 脚本 |
- **对策**：要真退出码就别接管道——bash 用 `${PIPESTATUS[0]}` 只是补救，cmd 里没有任何"管道后读回上游退出码"的字段，只能拆成两行不带管道。判定脚本成败用"退出码 + 关键输出行"**双证据**，不看"有没有报错文案"。
- **判定**：故意让脚本失败一次，对比 `echo $?` 与 `echo ${PIPESTATUS[0]}`；两值不同即确认你在读错的字段。**这条不只坑测脚本，也坑测命令**——本包 `git-ref-plumbing-on-windows §4` 有一条"git 静默失败"的记录就是这么来的：裸跑、命令替换、Node `spawnSync`、PowerShell 四种读法都拿到 **1**，只有中间隔了管道才是 **0**。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37 / cmd / Windows PowerShell 5.1.26100.9444 / Node v24.18.0 · 2026-09-17 首发，2026-09-18 第二次独立重跑，上表三行数字全部一致

## 2. 空输出有三种成因，先分清再解读

- **现象**：`if [ -n "$OUT" ]; then ok; else 网络失败; fi` —— 仓库确实没有待办 PR 时输出也是空，于是循环"重试网络"六次，每次都很自信。
- **根因**：把"结果为空"和"取数失败"塞进同一个信号。
- **对策**：失败判据用退出码或 HTTP 码，空值判据用 `--jq 'length'`（显式拿到 `0`）。反过来也成立：**批量删除/清理前，0 命中必须先证明过滤器有效**——喂一条"故意不存在的串"当对照组，同时喂一条已知存在的串证明能命中，然后再相信那个 0。
- **判定**：`git ls-remote` 不带代理时失败只写 stderr、stdout 全空，`| grep` 得空 → 极易被读成"分支已不存在"。看 stderr 与退出码即可分辨。
- **还有第三种成因（本机实测）**：命令链里某个**外部工具没装**。这台机器的 Git Bash 没有 `jq`，于是 `echo "sha: $(curl -s … | jq -r .sha)"` 打出来是**空串**，而**整条 `echo` 的退出码是 0**——子 shell 里那个真实的 `127` 被外层 echo 吞掉，`bash: jq: command not found` 只躺在 stderr。五个字段连着看，就 100% 像"上游 API 没返回这些字段"。
- **对策**：① 取值**别嵌在 echo 的参数里**，先 `v=$(…); echo "exit=$? value=[$v]"`，让子 shell 的退出码露头；② "字段为空"要当结论，先证明**取值通道本身取得到东西**——换一个必然存在的字段（如 `.id`）试一次；③ 能换就换宿主自带表达式引擎的 CLI（`gh api --jq` 不依赖外部 `jq`）。
- **判定（附带一个反直觉事实）**：逐名点工具，**别写 `command -v jq python git`**。实测它只打印找到的那几个名字，而且只要有一个命中就**退出 0**——`jq` 明明缺失，你拿到的却是"检查通过"。有效的写法是逐名循环：
  ```bash
  for c in jq python git; do command -v "$c" >/dev/null || echo "MISSING: $c"; done
  ```

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37 / Windows PowerShell 5.1.26100.9444 · python 3.12.10 · git 2.53.0.windows.2 · 2026-09-17
  （实测：`git ls-remote` 打不通的端口退出码 **128**（失败信号可用）；成功但无内容退出 0 且 stdout 0 字节；`jq` 缺失时命令替换的退出码是 **127**、取值 `[]`；`command -v jq python git` 多名字写法退出 **0**，逐名循环才打出 `MISSING: jq`。）

## 3. 取数失败会伪装成合法数据

- **现象**：逐个 `git log -1` 查远端分支的提交日期，得到**所有分支日期完全相同**。
- **根因**：拉取失败的分支回退到本地缓存/默认对象，日期是同一个兜底值。
- **对策**：多个分支日期全等 = 取数失败信号，不是"它们真的同一天"。要证据用 `git ls-remote --heads` 的 SHA 或 API。
- **判定**：同一条命令带上正确代理后日期即散开 → 确诊。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37 · git 2.53.0.windows.2 · 2026-09-17
  （实测：从未 fetch 的远端分支 `git log -1 origin/<b>` 退出码 **128**、stdout 空、stderr `fatal: ambiguous argument 'origin/<b>': unknown revision`——失败与"空值"可用退出码分开；权威取数用 `git ls-remote --heads` 输出 `<sha>\trefs/heads/<b>`。）

## 4. 远端 ref 的"假同步"：`packed-refs` 压过 loose 文件

- **现象**：`git fetch` 打印 `a..b main -> origin/main`，看着更新了，但 `git rev-parse origin/main` 纹丝不动；`git update-ref refs/remotes/origin/main <sha>` 也 exit 0 无效，甚至 `.git/refs/remotes/origin/` 目录已被 git 自己清掉，手写报 `No such file or directory`。
- **根因**：该 ref 只存在于 `.git/packed-refs`，loose 文件缺失时写入无处落，packed 条目继续胜出。
- **对策**：`mkdir -p .git/refs/remotes/origin` 后 `printf '%s\n' <sha> > .git/refs/remotes/origin/main`（loose 优先于 packed），再 `git rev-parse origin/main` 验证。
- **判定**：`git show-ref | grep origin/main` 看真实生效值 + `grep origin/main .git/packed-refs`。**这条最危险的后果**：此时 `git reset --hard origin/main` 会静默把工作树拉回旧提交。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37 · git 2.53.0.windows.2 · 2026-09-17
  （实测：`pack-refs --all` 后 loose 文件不存在、`packed-refs` 含该 ref；`update-ref` 目标给成分支名时报 `fatal: <name>: not a valid SHA1`、退出码 128；给成完整 SHA 后**退出码 0 但 `rev-parse` 纹丝不动**（静默无效，本机复现）；`mkdir -p .git/refs/remotes/origin` + 写入 loose 文件后 `rev-parse` 立刻变化。临时 clone 内完成，未碰真实仓库。）

## 5. 反过来的"假陈旧"：代理缓存了 ref  advertisement

- **现象**：刚合并完 PR，`git fetch origin main` 成功、exit 0，但 `origin/main` 指向几小时前的提交，当天合并的几条全"不见了"——看起来像远端被 force-push 回滚。
- **根因**：出口代理缓存了 smart HTTP 的 `GET /info/refs?service=git-upload-pack` 响应——这份 advertisement 里就是全量 ref 列表，客户端照着它挑 ref 更新；而 push 走 POST 不被缓存，于是出现"push 成功 / fetch 拉回旧状态"这种自相矛盾。
- **对策**：**换 URL 形态就换缓存键**（缓存层按完整 URL 建键），例如 `git -c http.proxy=http://127.0.0.1:<端口> fetch <换形态后的 URL> main`，再读 `git rev-parse FETCH_HEAD`。实测可用的两种改法：**去掉尾部 `.git`**、**换 host 写法**（`127.0.0.1` → `localhost`；对 GitHub 即 `github.com` ↔ `www.github.com` 这一类，`www.` 形态本轮未单独测）。**不要用加查询串**（`?cb=1`）：git 会把它拼进路径后报 `fatal: repository 'http://…/origin.git?cb=1/' not found`、退出码 128（curl 侧看到真实请求行被改写成 `GET /origin.git?cb=1/info/refs&service=git-upload-pack`、源回 404 ⇒ 它是死在源上，不是死在缓存上）。
- **判定**：用权威端点取真值 `gh api repos/<owner>/<repo>/branches/main --jq .commit.sha`，或 `git ls-remote` **绕过代理**直问远端。**权威说新、走代理 fetch 说旧 = 缓存问题，不是仓库问题**。换键追平后还要回头验一次**原 URL**：它走代理仍是旧的（换键 ≠ 清缓存），别把"下次又旧了"当成新故障。它与 §4、与"真·基线陈旧"（§6）症状几乎相同、处置完全相反，判错会做一堆多余的"补救"写回旧基线。

- **验证于**：Windows 11 家庭中文版 10.0.26200.9457 · Git Bash 5.2.37 · git 2.53.0.windows.2 · Node v24.18.0 · 2026-09-22
  （实测：本机自建假 origin（Node smart-HTTP，供 `/info/refs?service=git-upload-pack`）+ 本机 cache-first 代理桩（回显 `X-Cache: HIT/MISS`、按 URL 计数），**全程 loopback，不碰外网**。四组读数：① 源 `update-ref` 前进到 c2 后，走代理 `fetch` rc=0、stderr 空，客户端 `origin/main` 仍是 c1（假陈旧成立=True），同刻直连 `ls-remote` 与新＝真值含 c2 ⇒ 归因对照：把客户端拨回 c1、**只**把通道换成直连，`fetch` 就追平 c2（陈旧由代理缓存造成，不是 git 侧）；② 代理日志同一缓存键 `MISS` 后 `HIT`；③ 写侧另一半：`push` 新分支 rc=0 且直连全量 refs 里有它、走代理 refs 看不见 ⇒ 写侧当场生效、读侧看不见=True；④ 对策三写法：去掉 `.git` rc=0 拿到新值、host 换 localhost rc=0 拿到新值、加查询串 rc=128。收尾：换键追平后原 URL 走代理仍旧 c1（绕过靠换键不是清缓存）；最终代理计数 hits=5 misses=4 posts=2、缓存键 4 个。全部在一次性 scratch 目录与 loopback 端口内，未碰真实远端。）

## 6. 陈旧基线：把队友的产出整片删掉

- **现象**：本地克隆长期未同步，基于几天前的 `main` 开分支并推上去，PR diff 表现为**删除队友这几天全部产出**；评审方直接判定该分支禁止合并。
- **根因**：写操作前没 `git fetch`，或者 fetch 因网络静默失败却没被察觉（"我上次同步过"不是证据）。
- **对策**：任何写之前跑 `git fetch origin && git log --oneline -1 origin/main && git log --oneline origin/main..HEAD`；fetch 报网络错就**停止一切写操作**。合入别人的分支前查三样：`git merge-base <分支> main` 的年龄、`git diff --stat main..<分支>`（净删几千行且 0 新增）、`git ls-tree -r <分支> --name-only` 里关键文件还在不在。
- **判定**：任一异常即禁止合并；三重信号同时异常时不要"先合了再说"。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37 · git 2.53.0.windows.2 · 2026-09-17
  （实测：把 origin/main 冻结在旧提交后，`merge-base` 年龄显示"刚发生"、`diff --stat origin/main..HEAD` 是 `3 deletions(-)` 而 `--numstat` 给出 `0\t1\ta.txt` 形态=净删无对应提交；`ls-tree -r HEAD --name-only` 里关键文件缺失；真跑一次 `fetch` 后 origin/main 前进、幻影删除消失。全部在 temp 自建假目录内。）

## 7. `exit 0` 但事情没做成：GitHub 侧四例

- **`gh pr merge`**：**成功时它一个字都不说**（靶场仓 PR 实测：合并那一跳 **rc=0、stdout 0 B、stderr 0 B**），所以退出码 0 本身不携带任何"合成了"的信息，必须另做复核。它也可能**先失败再重试即过**：本轮首跳 rc=1、stderr 是 `GraphQL: Something went wrong while executing your query on <时间戳> …`；同层还有 `Post "https://api.github.com/graphql": EOF`、`TLS handshake timeout` 一族 ⇒ 这些是**通道**噪声，不是"合并被 GitHub 拒绝"。原记的"**退出码 0 而 PR 仍是 OPEN**"**两轮独立尝试各一次均未复现**（两轮最终都真合上了），而本轮找到了它最现实的产生方式 → 见下面"判定（写侧）"。合并动作之后必须复核 `gh pr view <n> --json state,mergedAt,mergeCommit` 看到 `MERGED`（口径别用错，见下）；`--delete-branch` 放到确认之后再单独补一次调用。
- **`PATCH` 返回 200 但字段没生效**（靶场仓实测坐实）：`PATCH /repos/<o>/<r>` 带 `topics` → **200**，响应体**有** `topics` 这个键、值是**改写前的旧值 `[]`**（不是省略键，是回显旧值），随后 `GET /topics` 与 `GET /repos/<o>/<r>` 两处读回都仍是 `[]` ⇒ 静默忽略。改 `topics` 要单独 `PUT /repos/<o>/<r>/topics` 带 `names` → 200，两处读回都变。**两条要紧的细节**：① 同一次 PATCH 里 `description` **生效了**而 `topics` 没有 ⇒ 这是**部分字段静默**，不能靠"别的字段确实变了"推断这一条也生效；② 形状写错时 **PUT 会明说、PATCH 只会沉默**——把 `names` 误传成双重编码的字符串（整个数组变成一整个字符串），PUT 回 **422** 且正文原样回显传进去的值：`For 'properties/names', "[...]" is not an array`。凡"API 调用成功但结果不对"，先 dump 一条原始响应看字段真实值与大小写（CI 的 `status`/`conclusion` 是小写 `completed`/`success`）。
- **403 正文里有关键信息**：只看状态码会漏掉可执行的下一步。实测一例**必须先看正文再看码**的形状：同一个只读 `GET /repos/<o>/<r>`，走共享出口代理时 403、正文是 `API rate limit exceeded for <那个出口 IP>. … Authenticated requests get a higher rate limit` + `documentation_url`，而**同一时刻换直连同一 URL 就是 200**。⇒ 这条 403 与"你没权限 / 仓库不存在"毫无关系，它是**通道**故障（未认证配额被同 IP 的人用光了），正解是带认证或换通道，不是去改仓库。原记的另一例（"make this repository public to enable this feature"，Pages 类功能未开）本轮**未复现**，按复盘保留。
- **推成功 ≠ 可访问**：仓库仍是 private 时页面 404，而 API 侧 commit 已存在。**这条本轮已实测**（读侧形状）：同一账号两个私有仓，鉴权 `GET /repos/<o>/<r>/contents` 读得到文件 ⇒ 推送与内容都在，未鉴权 `raw.githubusercontent.com/<o>/<r>/<branch>/<file>` 却回 **404**；而"该仓根本不存在"的 URL 同样回 404 ⇒ **对外看起来像仓库没了，不是权限问题**；同账号的公开仓 `README.md` 回 200 可作正控。（"页面 404"这一路本轮走的是 raw 形态，github.com 网页形态未单独取数。）

- **判定（读侧已实测的那条）**：凡"API 调用成功但结果不对"，先把**一条原始响应整条 dump 出来**，看字段的真实值与大小写——实测 CI 侧就是小写 `status='completed'` / `conclusion='success'`（同一仓库连续两条 run 字段形状一致），拿 `Success`/`COMPLETE` 去比会得到恒假的"还没完成"。
- **判定（写侧已实测）：同一事实 REST 与 GraphQL 用两套词汇，用错口径会造出恒假的"没合"**。靶场 PR 合并后：GraphQL 侧 `gh pr view --json state` = **`MERGED`**；REST 侧 `GET /pulls/<n>` = **`state='closed'` + `merged=true` + `merged_at` 非空 + `merge_commit_sha` 与 GraphQL 的 `mergeCommit.oid` 同值**；`GET /pulls/<n>/merge` = **204 / 0 B**。⇒ REST 的 `state` **只有 `open`/`closed` 两个值，永远不会是 `merged`**；拿 REST 的 `.state` 去比 `MERGED` 是恒假判据，读起来恰好像"rc=0 但 PR 还没合"——这比"远端真回了 OPEN"常见得多。最强的一条复核是**看 base 真前进**：本轮 base `<base sha> → <merge sha>`、README 6 → 8 行。**同一类口径差在 REST 内部还有一格**：列表端点 `/pulls?state=all` 的 PR 对象里**没有 `merged` 键**（实测 `'merged' in pr` = False，只有 `merged_at` 可判空），`merged` 只出现在单条 detail `/pulls/<n>` ⇒ 在列表侧写 `pr['merged']` 当场 KeyError，改成 `pr.get('merged')` 就得到恒假的"这个分支没合过"——而它正对着 §10 那条删除前置判据，方向是删错分支。
- **探针自己的两条坑（本轮踩到；与 GitHub 无关，但专门生产空白读数）**：① `cmd | tail -2; echo rc=$?` 量的是 `tail` 的退出码，不是 `cmd` 的——用 `${PIPESTATUS[0]}`，或先落盘再取 `$?`；② `subprocess.run(text=True)` 在 zh-CN 机器上按 gbk 解码 curl 的 UTF-8 正文 → reader 线程 `UnicodeDecodeError` → `p.stdout` 变 `None` → 下游 `AttributeError`，须显式 `encoding="utf-8"`。两条的表现都是"命令看着没问题，读数却空白／炸在下游"。

## 8. 计划任务：注册了，但永远不会跑

- **现象**：`schtasks /query` 显示 `Status=Ready`、下次运行时间也在未来，但从没真正执行过。
- **根因**：`schtasks /create` 默认写入 `<DisallowStartIfOnBatteries>true</DisallowStartIfOnBatteries>`、`<StopIfGoingOnBatteries>true</StopIfGoingOnBatteries>`、`<LogonType>InteractiveToken</LogonType>`。笔电没插电/没人登录 = 整轮丢失，而且不报错。（实测：`schtasks /query /tn <任务> /xml` 里三个元素俱在。）
- **对策**：注册后立即手动跑一次；笔电上把两个电池开关置 `false`；无人值守要换登录类型并配账号。判断"某个定时任务是否真的在跑"看它**日志尾部的时间戳**，不要看注册没注册。
- **判定（两条都要）**：
  1. `Get-ScheduledTaskInfo -TaskName X` 读 `LastTaskResult`，非 0 即失败，用 `New-Object System.ComponentModel.Win32Exception(<code>).Message` 解文案。实测某长期"看着健康"的任务 `LastTaskResult=2147946720`（`0x800710E0`）而 `Status` 依然正常。
  2. 别按英文标签 grep：中文 Windows 上 `schtasks /fo LIST /v | Select-String "TaskName|Status|Next Run|Last Result"` 实测返回 **0 行**（标签已本地化成"上次结果/下次运行时间"），而退出码仍是 0——于是被误读成"任务不存在"。验证一律走 `/xml`（标签恒英文）或 `Get-ScheduledTask*` 属性。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Windows PowerShell 5.1.26100.9444 / cmd（schtasks） · 2026-09-17
  （实测 `skills-auto-update`：`LastRunTime=2026/9/14 13:26:44`、`LastTaskResult=2147946720`（`0x800710E0`）、`NextRunTime=2026/9/21 9:00:00`、`State=Ready`；`DisallowStartIfOnBatteries=True`、`StopIfGoingOnBatteries=True`、`LogonType=Interactive`（XML 里为 `InteractiveToken`）；`schtasks /query /tn <任务> /xml | findstr` 英文标签命中、退出码 0，而 `/fo LIST /v`（中文本地化标签）对英文标签返回 0 行。**边界：本轮只读，未新建/修改/删除任何计划任务。**）

## 9. `curl` 打回了 HTTP 码，文件却没落盘

- **现象**：`curl -o out.json` 偶发有状态码、无文件，下一步读取报 `No such file or directory`（受限沙箱里更常见）。
- **对策**：要正文就别经文件，直接走 stdout 管道；要落盘就立刻 `test -s out.json && wc -c out.json`。
- **判定**：把 `-w "%{http_code}"` 与 `-s file -a -s file`（存在且非空）当成一对断言，缺一即视为失败。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · cmd / cmd(curl 8.21.0) / Windows PowerShell 5.1.26100.9444 · 2026-09-17
  （实测：连不通时 curl 打印 `http=000` 且**退出码 7**、两种落盘路径都不产生文件；健康 200 时 `-o <文件>` 落盘 7 字节。真坑是**不成对读**：只拿 `%{http_code}` 会看到 000 而以为"请求成功"，只 `test -s` 会在拒绝连接时缺少文件。两条断言（退出码/状态码 + 文件非空）必须成对。全部走 `127.0.0.1:<端口>` 本地回环，未打外网。）

## 10. 编辑工具会静默丢改动

- **现象**：同一条消息里对**同一个文件**发多个 Edit，每个都回 `Successfully edited`，最终只有一部分生效——新增的定义被同批的循环改动覆盖掉。另一形态：对日志/清单类文件"追加"，实为整段覆盖，历史静默消失。
- **根因**：并行 Edit 各自基于同一份旧快照回写，后写覆盖先写；追加语义被实现成全文件写。
- **对策**：同一文件的多处改动**必须串行**（一次消息一个 Edit），不同文件才可并行；追加时先 `Read` 尾部若干行，把尾部原样保留在新内容开头。
- **判定**：改完逐个复核"每个新增符号还在吗"（`grep -c`），以及行数/段落的增减是否符合预期。只读工具的返回文字必然漏。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Node v24.18.0（写入工具同构实验） · 2026-09-17
  （实测：对同一份旧快照并行写回两次，只留下后写的那处改动（`EDIT-A:false EDIT-Z:true`）；每次写前重读则两处都在；"追加"按整文件写会把旧内容清空，先读尾部再拼回则保留。）

## 11. 解释器"存在"是假信号

- **现象**：`command -v python3` 有输出、`Get-Command python3` 也成功，于是选定它写脚本；实际一跑零输出、退出码 49（实测 `python3.exe` 是 0 字节 `ReparsePoint` 桩，`python3 --version` 退出码 49 且 stdout/stderr 全空）。
- **根因**：`%LOCALAPPDATA%\Microsoft\WindowsApps` 在 PATH 上，里面是应用执行别名占位符而非可执行文件。
- **对策**：判定解释器可用性要**真跑一次并看退出码**（`python3 --version` / `python -c "print(1)"`），并把解释器路径写死成绝对路径；多解释器并存时用 `py -0p` 先列清，报"模块不存在"时先确认跑的是哪一个。
- **判定**：`Get-Item (Get-Command X).Source | Select-Object Length,Attributes`——`Length=0` 且含 `ReparsePoint` = 桩，视为不存在。同类：`npx`/`npm` 会同时投放 POSIX / `.ps1` / `.cmd` 三件套，cmd.exe、PowerShell、Git Bash 各取不同那份，所以"同一条命令在不同宿主行为不同"。

## 12. 重试环掩盖错误前提

- **现象**：同一目标动作反复进行（读同一文件、跑同一转换、试同一命令）而中间输出无变化，最坏一次耗掉整轮。
- **根因**：语义/逻辑类失败被当成网络抖动重试。只有网络类值得重试，且次数有限。
- **对策**：**无新进展的同类调用超过 3 次立即停**；止损顺序 = 换工具/换命令形态/换输入形式 → 仍不行就明确报告故障并给人工方案。区分三件事："我在重试" / "我在换办法" / "我在原地打转"。
- **判定**：对自己的调用日志计数——同一 `file_path` 或同一命令行出现 ≥4 次即已命中。

- **验证于**：Windows 11 家庭中文版 10.0.26200.9457（zh-CN）· Git Bash 5.2.37(1)-release(x86_64-pc-msys) · Python 3.12.10 · 2026-09-21
  （载体是**我自己的会话调用日志**（一份 JSONL，快照 2 616 条 `tool_use`）：把每条调用按不同口径配对计数，
  脚本可复跑，不需要外部工具。）
- **判据更正（同一快照下五种口径的命中数差一个量级）**：
  - **口径 A**（原文那句："同一 `file_path` 或同一命令行 ≥4 次"）→ **65 命中，其中 53 个每次输出都不同**。
    同一个文件被逐条改几十次、每次回执都不同，是正常工作形态 ⇒ 照原文执行，**误报八成**，会把"正在推进"读成"打转"。
  - **口径 B**（完整入参相同 + 输出哈希相同 ≥3）→ **7 命中**；逐条打开看全是重复查同一个工具 schema、
    以及写类工具那句模板化成功回执——**同形但无害**。这条反过来又**太严**（见 F）。
  - **口径 C**（把输出做"抹掉数字/路径"的归一化再比）→ **55 命中**，比 B 膨胀 7 倍：
    写类工具的成功回执本就是同一个模板（`Successfully modified file: <路径> (# replacements)`），
    归一化等于亲手把区分度销毁。**要判"输出没变"就用精确哈希，别归一化。**
  - **口径 D**（同一份**报错指纹** ≥3，不看输入变没变）→ **5 种指纹覆盖 42 条被拒回执**（全程 133 条被拒）。
    前三名：`File has not been read yet` 15 次、`old_string 0/多重命中` 11 次、`File has been modified since read` 10 次
    ——**全是前提类错误，一条都不是网络类**，正好落在这节的根因上。
- **本条的真正定义（F 给出的关键读数）**：把 D 再按目标文件收紧成"同一(工具, 对象, 报错首行) ≥3"，
  得 **3 簇 / 12 次被拒**，而**每簇每一次的入参都不同**（5 次 = 5 种入参、4 次 = 4 种、3 次 = 3 种）。
  ⇒ "命令在变"完全不能证明"在换办法"：**参数在动、前提没动，就是原地打转**。
  所以计数单位应当是**报错指纹**，不是命令行；同一份拒绝文案第二次出现时，该做的不是再改一个参数，
  而是回到产生这个前提的那一步（重新读、换锚点、承认过滤器无效）。
- **累计窗口**：同一簇的时间戳从 09-17 跨到 09-20（间隔中位数上百条调用）⇒ "超过 3 次立即停"要按
  **同一报错指纹的全程累计**数，不是按一次连击里的连续次数数；跨天复发说明那个前提一直没被修。
- **本轮未观测到的形态（别当常态）**：把条件收紧成"8 条调用之内凑够三连"后命中数为 **0**——
  这份日志里没有出现教科书式的紧凑死循环，原文"最坏一次耗掉整轮"那一种今天没复现。

## 13. 校验脚本自己会失效：对照没进扫描面、缺失文件被读成"内容不同"、整步静默跳过而后步全绿

- **现象**：同一轮收口里连撞三支，方向不同、同源。
  ① 对一棵树做禁词扫描得到 0 命中，为证明"过滤器会响"而往工作树写了个含清单词的临时文件再扫——**对照也不响**，看起来像扫描器坏了。实际原因是扫描用 `git grep`，它默认只搜**已跟踪**文件，那个临时文件从没进过索引，压根不在扫描面里。
  ② 扇出比对（仓库 vs 真相源，10 个文件逐一 md5）一次报 **10/10 全部 MISMATCH**，看起来是一场严重漏扇事故。实际是比对脚本的目标路径多写了一层目录，`md5sum` 对不存在的文件**不吐哈希**（只往 stderr 报错），命令替换拿到的是**空串**，于是字符串等值判断对每一项都判成"不等"。
  ③ 同一夜第三程（把那一节推上去之后再验一次）做"逐文件字节比对"时，脚本自身写错（对返回对象直接 `.split()`）抛 `AttributeError`，**整步没执行**；可它后面的门槛检查、以及"新节在不在远端树里"检查**全部通过**，末尾还接着跑了清理。要不是把这段单独重看一遍，就会拿"后面都绿"当作"每步都做了"。这一支比 ① ② 更危险：前两支好歹报出了一个异常数字，这一支**没有任何异常信号**。
- **根因**：校验的可信度来自三样东西——**扫描面**、**对照组**、**每步自己的成功读数**。任一坏掉，输出都和"真结论"长得一模一样。`git grep` 对未跟踪文件沉默；shell 把工具的失败折叠成空串。而假绿来自**语句分隔方式**：换行或 `;` 把多步串成各自独立的命令，前一步的失败对后一步完全无感（实测 A：中间步自己重跑退出码是 **1**，可后面那句 `ALL CHECKS PASS` 照样打印、末条退出码 **0**）；反倒是 `&&` 链**不会**这样（实测 B：链在失败步断掉，后一步根本没跑，末条退出码 **1**）——所以"用 `&&` 串起来"是有效防线，而**写成多行**不是。反过来这支也存在：出门内容里若混进一个**当时还没被跟踪**的文件，扫描面就漏了它，那 0 命中是假干净。
- **对策**：① 对照样本必须**确实在扫描面里**——用 `git add -N <单个文件>`（intent-to-add，不把内容写进索引）让它进入 `git grep` 视野，验完 `git reset -- <该文件>` 删掉；或直接用自带脏样本的 `check.py selftest`。② 比对脚本先测**存在性**再测内容，并把两类失败分开打印（`ABSENT` vs `MISMATCH`）——只有一个笼统"不一致计数"时，路径写错与内容被改读起来完全相同。③ 报告里带上 `files=N` 总数：**全量不一致（问题数 == 总数）几乎总是测量错**，局部不一致才可能是真漏扇。④ 拿到哈希先判空：`[ -z "$b" ]` 单列一支，别让它进等值比较。⑤ 最终扫描面用**全新 clone 的那份树**，它天然等于出门内容，不必再推断工作树与提交是否同一集合。⑥ 多步检查**要么用 `&&` 串成一条**（失败步之后根本不会跑），**要么每步各回显一份读数**（比对了几个文件、拿到什么 SHA、显式打印 `exit=$?` 再读）；**写成多行不算任何一种**——那是实测里唯一"零信号"的形态。取读数本身也有坑：`var=$(a | b)` 之后再读 `${PIPESTATUS[0]}` 得到的是**赋值语句的 0**，不是管道首段的退出码（实测那样读到 `exit=0`，而同一函数单独跑是 1），要拿就在替换内部或紧接其后单独取。
- **判定**：对任何 0 命中或全量命中，先回答一句——"这个数字是在**真的扫描面/比对集**上得到的，还是在工具悄悄跳过的那部分上得到的？" 可执行的证法有两级：**(a) 扫描面**——同一轮里放两个对照样本，一个**已知在扫描面内**、一个**已知在扫描面外**（未跟踪文件即天然如此），只有前者命中、后者不命中，才算"过滤器有效 **且** 扫描面已证"；只测前者会漏掉 ①，只测后者会误判成扫描器坏了。**(b) 链条完整性**——往检查里**注入一次失败**（送一个不存在的路径、或让某步 `exit 1`），然后看那句总结论还打不打得出来：`&&` 形态下后半段应当消失（实测末条退出码 **1**、`ALL CHECKS PASS` 未打印）；多行形态下若总结论照样打印（实测末条退出码 **0**），说明这一步的产物没被任何下游消费，这个"通过"不能采信。
- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37（MSYS 3.6.6 / git 2.53.0.windows.2）· Python 3.12.10 · 2026-09-18（首发当日连补三支）
  （实测：`git grep -F <清单词>` 对一个含该词的**未跟踪**临时文件报 0 命中；同一文件 `git add -N` 后立即命中 1，`git reset -- <该文件>` 并删除后 `git status --porcelain` 恢复为空。②：`md5sum <不存在路径> | awk '{print $1}'` 得空串，与真实哈希比较判为不等 ⇒ 10 个技能全报 MISMATCH；纠正路径层数并加 `[ ! -f ] → ABSENT` 分支后重跑，同一批 10 项一致、缺失 0 项。③：同一轮第一版脚本整段因 `AttributeError` 未执行，其后门槛检查仍报 `0 error`、`grep -c '^## 13\.'` 仍得 1；重跑并在末尾显式打印 `exit=0` 与逐文件计数，才得到 `tracked=16 ABSENT=0 BYTE-MISMATCH=0` 这份真实读数。链式形态对照（**同一个必然失败的函数**，只改语句分隔方式）：多行/`;` 形态 ⇒ 失败步单独重跑退 **1**，但总结论照样打印、末条退出码 **0**；`&&` 形态 ⇒ 后半段未执行、末条退出码 **1**；`r=$(失败 | wc -l)` 形态 ⇒ 读数是 `lines=0`（空输出即信号），而随后读 `${PIPESTATUS[0]}` 得 **0**（赋值自身的状态）。）
- **补一支（2026-09-29，同一族里"我写的兜底文案盖掉了唯一正确的读数"）**：跑一个 `.ps1` 时落盘名是 `pi-junction-shellpath-…ps1`、我在命令行里敲的是 `pi-junction-shell-quoting-…ps1`（差一段），PowerShell 立刻回了**足够**的诊断「`-File` 形式参数…不存在」。但我在末尾挂了 `|| echo "RUN_FAILED (可能脚本未落盘)"`：① 这句 `echo` 自身成功 ⇒ **整条命令退出码 0**；② 它把原因写成我的猜测（"未落盘"），真因却是"我打错文件名"——我差点据此去重跑落盘而不是改名。
- **对策**：失败分支**要么不写，要么只写动作**（`|| echo NEXT_STEP_LS`），绝不把自己的**原因猜测**印成输出当结论；判"到底跑到了哪个文件"让命令自己回显 `Resolve-Path` 或产物哈希，而不是靠我起的名。与 ② 同族：**两次都是"以为在测 A、其实测的是 B"**，这次区别只在 B 根本没存在。
  （09-29 实测：错名那次 stdout = 版权横幅 + `-File 形式参数…不存在`，`echo` 分支被执行、整条退出码 **0**；换成正确名后同一脚本输出 `CREATED: …\shell-quoting-and-path-forms` + `READABLE len=66714 sha=1bbf06713c95`，与源文件 `sha256sum` 前 12 位**逐字相同**——"跑到了哪个文件、字节是否等于源"这一句读数把两类失误一次合并解决。）

## 14. "命中 N 处"没有分母就不是证据：同一批字节报出 19 与 77 两边都对；两套口径数字相同则是去重静默失效

- **现象**：一次公开历史清除任务里，同一份历史（37 笔提交）、同一批四类身份字面量、两个扫描器，报出 **19 处**与 **77 处**两组命中数（逐类分别 12/2/3/2 与 25/13/25/14）。双方都确信自己扫的是全量，第一反应"对方扫错了"——方向就是错的，**两边都没扫错**。
  同族第二支更安静：同一份脚本里两套口径输出**完全相同的两列**（控制词 `MIT` 报 `111 / 111`），据此写出的"去重之后仍然是这个数"是假的。
- **根因**：
  - ① **分母没进报告**。git 历史天然按引用摊开，至少两个合法口径：**唯一对象口径**（按对象 sha 去重 ⇒ "服务器上存几份、改写要动几个对象"）与**逐笔实例口径**（按 `(commit, path)` 走 ⇒ "翻历史时会看到几次"，同一个脏 blob 被 37 笔提交带着就记 37 次）。两个都合法，回答的是不同问题，混在一张表里才出事。
  - ② **去重键写错，且静默**。实测两种错法：`for _m, sha in tree.items()` 少解一层（`dict.items()` 的 value 本身又是 `(mode, sha)`，于是集合收进去的是 path 和元组，永远命不中）；以及键**类型不一致**（一处 `add` 的是解码后的 `str`，一处 `in` 比较的是原始 `bytes` ⇒ `b"x" in {"x"}` 恒为 False）。两者都不抛异常、不改输出格式，只把"每个对象数一次"退化成"每笔都数一次"。**最阴的一点：退化后的 77 恰好等于另一个合法口径的值**，所以它看起来不像错数，像"另一种数法"。
- **对策**：
  - 任何"命中 N"必须写成 **N + 分母定义**（去重键是什么、扫的是哪些对象），并**同批带一个必然跨提交重复的控制词**报两列数。控制词那一行不动而目标词动了 = 内容变了；两列一起动 = 扫描面或口径变了。
  - 拿到别人的数字**先复跑对方口径**再谈谁错。本程按"逐笔实例"重算对方的三个数，逐格一致，争论当场消失。
  - **两套口径的数字完全相同 ⇒ 默认判"我的去重没生效"**，去查键，不要先接受"恰好相等"。只有当你能一句话说清"为什么必然相等"（例如扫描面只有一个提交、或全包没有任何 blob 被两笔以上提交复用）才允许相等。
  - 写键的规矩：元组显式拆开 `for path, (mode, sha) in tree.items()`；类型全用同一种（要解码就在**入口**处解一次，不要在 `add` 处解、在 `in` 处比 bytes）。
- **判定**：一条命令证伪"去重在生效"——拿一个必然跨提交复用的 blob，比"引用它的提交数"与"不同 sha 数"：
  ```bash
  git rev-list main | while read c; do git rev-parse -q --verify "$c:LICENSE"; done > /tmp/blob-list.txt
  echo "refs=$(wc -l < /tmp/blob-list.txt | tr -d ' ') distinct=$(sort -u /tmp/blob-list.txt | wc -l | tr -d ' ')"
  ```
  本机实测输出 `refs=37 distinct=1`。⇒ **一份 blob 被 37 笔引用，而你的"唯一对象"列也报了 37，就是去重没生效**。
  报数时还要写清分母是哪一层：`git rev-list main | wc -l` 给出提交数（本机 37），`git rev-list --objects main | wc -l` 给出对象数（本机 260）——同一批字面量在这两个分母上必然不同。revs 一律**显式写**（本机 `--all` 曾把改写工具留下的 `refs/original/*` 一起算进来，于是"改写成功后仍报 19 处"，白查一轮）。`wc`/`sort` 之后别用管道读 `$?`（见本文件 §1）。
- **验证于**：Windows 11 家庭中文版 10.0.26200 · Git Bash 5.2.37（MSYS 3.6.6）· git 2.53.0.windows.2 · Python 3.12.10 · 2026-09-19
  （实测读数：同一份 37 笔 / 89 个不同 blob / `rev-list --objects` 260 个对象的历史上，唯一对象口径 12/2/3/2 = **19 处**、载体对象 **12 个**（11 个 blob + 1 条 commit message）、"词 × 对象" **14 对**；逐笔实例口径 25/13/25/14 = **77 处**；控制词 `MIT` 同两列 **17 / 111**，去重修复前是 **111 / 111**，修复后 17 / 111。②的第二种错法（键类型不一致）实测把合计打成 **77**。同日两次独立连跑逐格一致。）

## 14b. 本节这套两口径计数，落地场景是"密钥进 git 历史后的清除"

上面 §14 的所有读数都出自一次真实的**历史清除任务**——清除动作本身（扫描面清单、先副本后原件、`refs/original/*` 别混进 `--all` 分母、远端可达性不可证、轮换与清除的先后）已成独立一颗：`git-history-secret-erase`。要"报命中 N 处之前先固定口径"读这里；要真的动手清历史，去那颗按 SOP 走。

## 15. 守卫/检查本身从没生效过：条件恒假与恒真

前面各节讲的是"命令的成功信号为真、事实为空"。这一节更靠上一层：**做判定的那段代码自己没生效**。
两种形态都静默，而且**症状会被误读成别的问题**。

### (a) 条件恒假 —— 写法错，守卫形同虚设

实测（批处理里的端口占用守卫）：

```
netstat -ano | findstr /r /c:"LISTENING.*:<端口>"      →  命中 0 行
```

根因不是正则写错，是**列序理解反了**。netstat 的列是「本地地址:端口 … 远端地址  状态」——
**状态在端口之后**，所以 `LISTENING.*:<端口>` 这个先后顺序永远不可能成立。

后果链条（每一步都长得像别的问题）：守卫从不触发 → 脚本以为端口空着 → 起第二个实例 →
`EADDRINUSE` 退出 → **空重试 3 次** → 打印"连续 3 次退出"。
用户看到的是"启动脚本坏了"，真因是"守卫是死代码"。

**对策**：

- **每个守卫都要拿真实输入验一次真值，且正反两侧都验**：一个必然命中的输入 + 一个必然不命中的输入。
  实测：`:<端口> ` + `0.0.0.0:0` → 命中 **1** 行；把同一表达式换成 `:<端口2> ` → 命中 **0** 行。两侧都对才敢用。
- **优先用不依赖本地化词的判据**：`findstr /c:"0.0.0.0:0"`（远端全零）比 `findstr /i "LISTENING"` 稳 ——
  状态词在别的语言/版本里未必是 `LISTENING`。
- **防误伤**：`ESTABLISHED` / `TIME_WAIT` 行的远端是**具体地址**（`127.0.0.1:xxxxx`），
  用「本地端口 + 远端 `0.0.0.0:0`」两段过滤就把它们自然排除了。

**恒假的第二种来源：条件写得对，喂给它的量是错的**（实测于 agent-bridge 供应方熔断，2026-09-29）。
熔断要三条 AND 同时成立：`失败` ∧ `零进展` ∧ `扫到额度文案`。两条各自坏掉：

1. 文案表里没有 `usage limit`，而订阅额度到顶的原文恰好是它——那一次响应**连 402/429 都没有**，
   状态码这一层根本没给读数（文案只落在 CLI 自己写的 jsonl/轨迹/stderr 里）。
2. "进展"取自 `item.completed` 计数，而 `item.type === "error"` 那一条也在计数 ⇒ 实测 items=2 而实际零进展，
   第二条 AND 恒不成立。

后果与端口那个样本同形：熔断器**看起来在**（配置读了、函数调了、日志正常），实际一次都没合过，
同一张卡连派数日纯烧钱。**加一条对策**：验这类复合条件时，输入必须是**实录产物**（把那次真失败留下的目录离线重放一遍），
不能只用理想构造的样本——理想样本会顺着你对条件的理解去写，恰好看不见你理解错的那一项。
机制细节见 `realtime-task-bridge §8`。

### (b) 条件恒真 —— 哨兵值把不同原因压成一个

`catch` 里返回与其他分支同形的哨兵值，会让"正常但形态不同"也落进异常分支。
实测形态（详见 `hot-patching-live-artifacts`）：`catch { return null }` 使"目录不存在"与"读失败"无法区分，
判定恒真 → 告警**恒亮 2213 行 / 40 小时**。

**对策**：`catch` 里别返回同形哨兵值；先分形态（`existsSync` / `statSync().isDirectory()`）再判异常。
通用问句：**"还有哪些正常情况会走到这个 `catch`？"** 答不上来就先别信它。

### 共同判据

**守卫必须能报出它"检查过了"**。一个从不触发、也从不留下"已检查"痕迹的守卫，
与"它坏了"在外部**完全不可区分** —— 这正是它能坏很久没人发现的原因。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Windows PowerShell 5.1.26100.9444 · 2026-09-19
  （实测读数：`LISTENING.*:<端口>` 命中 **0** 行；`:<端口> `+`0.0.0.0:0` 命中 **1** 行、`:<端口2> ` 命中 **0** 行；
  修好的脚本实跑 exit **1** 并打印"已被占用"；恒真告警 40 小时 **2213** 行、修复后 95 s 窗口 Δ=**0**。）

## 16. 存在性证据：HTTP 200 和"端口未监听"都可能是假的

- **200 ≠ 存在。** SPA 的 fallback 让**不存在的路由也返回 HTTP 200**（返回 `index.html`）。
  实测本机该 fallback 固定 **13556 字节**。曾拿 200 当"路由活着"，白排查两轮。
  **对策**：测路由看**响应体长度/内容**，或拿一个已知不存在的路由做对照；
  把 fallback 的字节数当常数记下来，一眼分辨。
- **反向形态：完全不响应，既不是 200 也不是拒连。** 上面那一支好歹还有信号可读（一个码）。当请求**永远挂着不返回**时，"没信号"极易被读成"服务死了"，而三种成因的处置完全不同：进程根本不在 / 进程在但 0% CPU 卡在无上界的等待 / 进程在且打满一个核（事件循环被同步代码饿死）。这一族的判形与现场取证不在本颗，走 `live-state-forensics`。**本颗留给这条的教训是：不要把"取不到读数"直接写成"它没在跑"**——那与 §2 的"空输出有三种成因"是同一个错误，只是发生在服务层。
- **探测通道自己会被限制。** 实测：`Get-NetTCPConnection -LocalPort <端口> -State Listen` 返回**空**，
  而同一时刻 `Invoke-WebRequest http://127.0.0.1:<端口>/` 返回 **200 / 13556 B**。
  ⇒ "查不到监听"是**探测被挡**，不是"服务没起"。
  **对策**：结论别建立在单一通道上，用**功能性探测**（真的发一个请求）交叉验证。
  报"服务没起"之前，必须先解释**"那这个 200 是谁回的"**。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · Windows PowerShell 5.1.26100.9444 · 2026-09-19
  （实测：fallback 恒为 13556 B；`Get-NetTCPConnection` 空 vs `Invoke-WebRequest` 200 同时成立；
  三条真实路由实测 44044 / 1816 / 3977 B，均非 13556 故判定为真实响应。）

## 17. 识别/生成类工具：返回成功，内容却是编的

这是 §3「取数失败伪装成合法数据」的**升级版** —— 伪装得更彻底：有完整句式、有细节、**有信心**。

- **实测**：把一张界面截图裁出 248×204 的区域交给视觉模型，它**自信地**描述成
  "舞台灯光光束 / 深色背景 / 橙紫色渐变 / 专业灯具" —— 与内容毫无关系，全程**没有一丝不确定语气**。
- 换一条**独立通道**（本地 OCR）判同一张图：`图中没有文字` → 与"这是一个无文字的小球/图标"相符。
  **两条通道交叉，才定下真实情况。**
- **对策**：
  1. 识别类工具的"成功返回"**不是**内容正确的证据。
  2. 用**两条独立通道**交叉（视觉模型 / OCR / 像素与尺寸统计），不一致时以**可测量**的那条为准。
  3. **未经交叉验证的识别结论不得写进交付物。** 实测决策：宁可**不放**截图，
     也不放一张由会编造的模型产出的图 —— 尤其当该项目的核心主张正是"不要无条件相信输出"时。
  4. 返回**结构化字段**（坐标 / 标签）时也要做几何或语义自检：坐标是否越界、标签类别是否吻合。
     实测：定位工具给出的框**落在图内**但内容无关 —— 仅靠坐标合法性**发现不了**，
     必须回到内容层面验证。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · 2026-09-19
  （实测：视觉链描述同一张界面裁图为"舞台灯光光束"；OCR 通道判"图中没有文字"；
  ground 返回框 (1234,678)-(1456,864) 落在 1536×864 图内但内容不符 → 结论以 OCR 为准。）

## 18. 渲染层静默失效：样式覆盖内联属性、主题变量反向解析、布局差一列

UI 层这一族和前面各节同一个形状：**不报错、输出「看着有内容」，但结果不是你要的**。
三支都是实测踩到的。

### (a) 样式表会覆盖内联属性 —— 选择器写宽了就把不该改的也改了

```css
.map-node rect { fill: rgba(255,255,255,.05) }
```

SVG 里同组还有个 4px 宽的色条 `<rect fill="#e0a458">` —— **也被这条命中**。
CSS 的 `fill` 优先级高于 SVG 的 `fill` **属性**（presentation attribute）⇒
色条被涂成近透明，**「同一大块同色」这个功能自始至终没生效过，而报错 0 条**。

**对策**：选择器按**类名**精确命中（`.node-bg` 只给框吃 fill），
别用「容器 + 元素名」这种会误伤同层兄弟的写法。

### (b) 主题变量可能解析成相反的值 —— 只给一种主题兜底等于没兜

```css
background: var(--panel-bg-l1, rgba(0,0,0,.14))
```

兜底只在变量**未定义**时生效。实测该变量在用户主题里解析成 `#f8f8f8` ⇒
整块地图变白板（截图取色：近白占 5.9%）。

**对策**：**底色不要依赖跨主题变量**（用 `transparent` 或自己的中性半透明色）；
文字色可以依赖。要么两套主题各实测一遍。

### (c) 布局差一列 —— 程序全绿，图是错的

```js
posOf(depth) = PAD_X + (depth - 1) * COL_W   // depth=1 → PAD_X
rootPos.x    = PAD_X                          // 根也在 PAD_X ← 重叠
```

深度 1 与根画在同一列，根被压住。节点数正确、连线正常、SVG 合法 ⇒ **没报错**。
用户看图才发现：「最左边不是根，而是一堆一级枝干。」

**对策**：布局算完跑**不变量断言**，别只看图：
- 同一列（同一 x）不得出现两个不同深度
- 任一节点框不得与父节点框重叠
- 画布宽高 ≥ 最右 / 最下节点 + 框尺寸
- 把每个节点的 `{id, depth, x, y}` 打出来扫一眼 —— 同列同 y 立刻现形

### (d) 渲染入口的运行时错会塌成**空白面板** —— 语法/构建全过

改布局时把 `var wrap = treeRow(...)` / `var svg = svgEl('svg')` 两行整段替换掉却忘了补回，
`wrap.appendChild(svg)` 里的 `svg` 是 undefined ⇒ 第一次 appendChild 就 `ReferenceError`，
**整个页签一片空白**。而 `node --check` 只查语法、构建成功、布局自检也全过。

**这是最糟的失败形态：用户不知道坏了，也不知道坏了哪一段**（截图里只有空白，
连"这是个错误"都不是）。用户的原话是「树怎么显示不出来了」——他能报告的只有"没有"。

**对策（两条都要）**：
1. **渲染入口套 try/catch，把错误本身显示在面板上**（不是只 `console.error`）——
   `console` 用户不会去看。空白是零信息，一段红底栈是满信息。
2. **验证必须真跑一次渲染**：`vm` + stub DOM 加载真实前端脚本，真的点一下页签、
   真的展开，然后断言产物数量与 `console.error` 为空。**"能 build" 和 "挂上去了" 都不能替代它。**

### (e) 派生数量对不上：连线全丢而"节点数正确"

父子连线一条都没画出来（服务端给的 `parent` 已是 `"R3"` 形式，前端又拼了一次前缀
⇒ 查 `"RR3"` 永远查不到）。**布局对、节点数对、SVG 合法、无报错** —— 只有"线"没了。

**对策**：自检要挑**派生量**，不能只数"我以为对的那个量"。
本例外每个非根节点恰好一条连线，所以断言 `edgeCount === flat.length`；
改成只数节点（`nodes === 60`）就完全抓不到。

- **派生量清单**：连线数 = 非根节点数；颜色块数 = 分组数；表头数 = 层数。
  数"结构自己生成的量"，不只是数输入条目。
- **同一份数据在两处渲染（界面 + 离线导出脚本）** 时，两处都要有同一条断言，
  且必须同源同改 —— 只改一处，界面和导出图会静默不一致。

### 共同判定

**「能渲染 / 有内容 / 不报错」都不构成「图是对的」。**
UI 类改动的验证要落到**可测量**的东西：取色、坐标、派生量断言。
只看截图（甚至只看缩略图）会漏 —— 本条五支里有三支就是这么漏掉的。
再补一句最省事的判据：**问自己"如果这段完全没生效，屏幕上会长什么样"**——
若答案是"和现在一样"，那这一处现在就没有任何证据。

- **验证于**：Windows 11 家庭中文版 10.0.26200 · 2026-09-19
  （实测：色条区裁图取色 #e0a058 占 22%，即 phase 色 #e0a458；修前地图区 #f8f8f8 占 5.9%、
  修后 #101018；maxDepth=10 时画布 2091px 但深度 1 与根同列。
  回归页：被修项目仓库内的一个 CSS 主题检查页（私有仓库，不随本包发布）。
  (d)：删掉两行后 `node --check` 与 `npm run build:client` 均通过、面板全白；
  (e)：60 个节点只画出 10 条根连线，改 `byKey[f.n.parent]` 后 `path=60`、`edgeCount=60`。
  冒烟：同项目的一个客户端渲染脚本（私有仓库，不随本包发布）。
  本节的项目名与 CSS 变量名已中性化，读数与判据未改。
  2026-09-21 复核：上一句当时**不成立**——两个带项目前缀的类名与两个私有文件路径仍在文中，
  已全部改为通用写法（类名 `.map-node` / `.node-bg`，私有页面只称"一个 CSS 主题检查页"）；
  色值、百分比、像素与 node/edge 计数等实测读数一字未动。）
